# Хранение заявок в Yandex Cloud YDB в России

Актуальность инструкции: 11 сентября 2026 года.

Эта схема предназначена для сайтов, которые принимают имя и телефон посетителя. Первая запись заявки выполняется в базе Yandex Database (YDB) в российском регионе `ru-central1`. В Telegram отправляется только обезличенное уведомление с идентификатором заявки. Имя и телефон нужно смотреть в YDB или в отдельной защищённой панели.

Регулятор персональных данных — Роскомнадзор, а не Роспотребнадзор. Российская база сама по себе не делает сайт автоматически соответствующим всем требованиям 152-ФЗ: также нужны корректные документы, уведомление Роскомнадзора, ограничение доступа, сроки удаления и фактическое соблюдение описанного порядка.

Основание для локализации — [часть 5 статьи 18 Федерального закона № 152-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_61801/cbf4e15b7c330f9372e876cdf2bc928bad7950ef/). Для владельца сайта, который собирает данные посетителей, Роскомнадзор разъясняет обязанность оператора и порядок уведомления на своей [странице для операторов персональных данных](https://82.rkn.gov.ru/directions/pers/p15375/).

## 1. Что будет входить в бесплатный лимит

Для YDB нужно выбрать **Serverless**, а для функции — **Yandex Cloud Functions**. По состоянию на дату этой инструкции бесплатный месячный объём на один платёжный аккаунт включает:

- YDB Serverless: первые 1 000 000 Request Units;
- YDB Serverless: первый 1 ГБ фактически занятого хранилища;
- две автоматические полные резервные копии за последние два дня;
- Cloud Functions: первые 1 000 000 вызовов;
- Cloud Functions: первые 10 ГБ·часов вычислений.

Лимит общий для платёжного аккаунта. Если к нему привязаны несколько облаков, каталогов, функций, баз и сайтов, их использование складывается. Неиспользованный остаток на следующий месяц не переносится. После превышения бесплатного объёма Яндекс начинает считать оплату по тарифу, поэтому это бесплатный вариант только пока суммарное потребление остаётся внутри лимита.

Для обычных заявок фотографа эти лимиты очень большие, но абсолютного запрета на списание средств они не создают. Чтобы снизить риск расходов:

1. Не создавать Dedicated YDB, виртуальные машины и управляемые серверы.
2. Выбрать YDB **Serverless** и нагрузку **OLTP**.
3. Оставить подготовленную пропускную способность равной нулю, то есть оплату по фактическим запросам.
4. Если интерфейс позволяет, установить максимальный размер хранилища 1 ГБ и небольшое ограничение пропускной способности, например 10 RU/с.
5. В Billing включить уведомления о бюджете. Уведомление предупреждает о расходе, но не является жёстким техническим ограничителем.
6. Раз в месяц проверять Billing → Детализация и показатели YDB.

Официальные документы:

- [Бесплатный объём Serverless](https://yandex.cloud/ru/docs/billing/concepts/serverless-free-tier)
- [Тарифы YDB Serverless](https://yandex.cloud/ru/docs/ydb/pricing/serverless)

## 2. Целевая схема

```text
Браузер клиента
    │ HTTPS POST: имя, телефон, согласие
    ▼
Yandex Cloud Function, ru-central1
    │ 1. Проверяет данные и согласие
    │ 2. Создаёт серверную дату и идентификатор
    │ 3. Сначала записывает заявку в YDB
    ▼
YDB Serverless, ru-central1
    │
    └── Cloudflare Worker → Telegram: только «Новая заявка ID …»,
        без имени и телефона
```

Форма должна обращаться прямо к адресу `https://functions.yandexcloud.net/...`. Cloudflare Worker можно сохранить для доставки обезличенного уведомления в Telegram, поскольку этот маршрут уже доказал свою работоспособность. После записи в YDB функция передаёт Worker только случайный `submission_id`, название сайта и тип события. Имя, телефон, способ связи и текст согласия Worker не получает. Cloudflare также можно оставить для DNS, HTTPS, кэширования статического сайта и защиты домена. GitHub Pages остаётся хостингом статических файлов и не получает тело заявки.

## 3. Создание YDB Serverless

1. Открыть [консоль Yandex Cloud](https://console.yandex.cloud/).
2. Выбрать облако `cloud-thealexmay` и каталог `default`, в котором уже находится функция `photoprobiz-leads`.
3. В списке сервисов открыть **Managed Service for YDB**.
4. Нажать **Создать базу данных**.
5. Указать имя `photoprobiz-leads-db`.
6. Выбрать тип **Serverless**.
7. Выбрать профиль нагрузки **OLTP**.
8. Не включать подготовленные вычислительные ресурсы.
9. Установить максимальное хранилище 1 ГБ, если это поле доступно. Если минимальное значение в интерфейсе больше, плата всё равно считается по фактически занятому месту, но нужно следить за объёмом.
10. Включить защиту от удаления, если настройка доступна.
11. Создать базу и дождаться состояния **Running**.
12. На странице обзора скопировать поле **Эндпоинт**. Разделить его по фрагменту `/?database=`: часть слева станет `ENDPOINT`, часть справа вместе с начальным `/` станет `DATABASE`. Эти значения не являются паролем или ключом.

Официальная инструкция: [создание и управление YDB](https://yandex.cloud/ru/docs/ydb/operations/manage-databases).

## 4. Сервисный аккаунт и права

Для функции нужен отдельный сервисный аккаунт. Не следует давать функции роль `editor` на всё облако и создавать постоянный статический ключ.

1. Открыть **Identity and Access Management** → **Сервисные аккаунты**.
2. Создать аккаунт `photoprobiz-leads-sa`.
3. Открыть созданную базу YDB → **Права доступа**.
4. Добавить сервисный аккаунт и назначить ему роль `ydb.editor` только на эту базу.
5. Открыть Cloud Functions → `photoprobiz-leads` → создать новую версию.
6. В поле **Сервисный аккаунт** выбрать `photoprobiz-leads-sa`.
7. Не создавать JSON-ключ и не помещать ключ сервисного аккаунта в код или переменные окружения. Прикреплённая к функции учётная запись получает краткоживущие полномочия автоматически.

Роль `ydb.editor` позволяет функции создавать схему и читать/записывать строки. После создания таблиц можно отдельно пересмотреть права, если Яндекс добавит более узкую роль для записи данных. Официальная справка: [управление доступом YDB](https://yandex.cloud/ru/docs/ydb/security/).

## 5. Таблицы

Практично использовать две таблицы:

- `leads` — рабочая база заявок, срок хранения обычной необработанной заявки до одного года;
- `consent_events` — доказательство данного согласия, срок хранения три года после окончания обработки или отзыва, как указано в документах сайта.

Рекомендуемые поля таблицы `leads`:

| Поле | Тип | Назначение |
|---|---|---|
| `submission_id` | Utf8, primary key | уникальный идентификатор заявки |
| `server_received_at` | Timestamp | доверенное время приёма сервером |
| `consent_accepted_at` | Timestamp | время установки галочки в браузере |
| `consent_version` | Utf8 | версия текста согласия |
| `form_id` | Utf8 | форма, из которой пришла заявка |
| `source` | Utf8 | домен сайта |
| `name` | Utf8 | имя клиента |
| `phone` | Utf8 | телефон клиента |
| `contact_method` | Utf8 | выбранный способ связи |
| `package_name` | Utf8? | выбранный пакет, если есть |
| `status` | Utf8 | `new`, `contacted`, `closed`, `deleted` |
| `expires_at` | Timestamp | дата автоматического удаления |

Рекомендуемые поля `consent_events`:

| Поле | Тип | Назначение |
|---|---|---|
| `submission_id` | Utf8, primary key | связь с заявкой |
| `server_received_at` | Timestamp | время регистрации на сервере |
| `consent_accepted_at` | Timestamp | время согласия в браузере |
| `consent_version` | Utf8 | версия согласия |
| `form_id` | Utf8 | идентификатор формы |
| `source` | Utf8 | домен сайта |
| `name` | Utf8 | субъект, давший согласие |
| `phone` | Utf8 | контакт субъекта |
| `expires_at` | Timestamp | дата удаления доказательства |

В реализации photoprobiz таблицы создаются автоматически при первой корректной заявке. Сервисному аккаунту для этого выдана роль `ydb.editor` на конкретную базу. Для `leads.expires_at` задан TTL один год, для `consent_events.expires_at` — три года. TTL помогает соблюдать сроки, но его срабатывание не следует считать мгновенным, поэтому удаление по отзыву выполняется отдельной командой сразу.

Официальные материалы:

- [создание объектов схемы YDB](https://yandex.cloud/ru/docs/ydb/operations/schema)
- [TTL в YDB](https://yandex.cloud/ru/docs/ydb/concepts/ttl)

## 6. Подключение функции

После создания базы код функции нужно изменить следующим образом:

1. Добавить официальный Node.js SDK YDB в `yandex/lead-function/package.json`.
2. Добавить в настройки версии функции значения Endpoint и Database из обзора YDB.
3. Использовать авторизацию через прикреплённый сервисный аккаунт.
4. Проверять имя, телефон, домен, форму, версию и факт согласия так же строго, как сейчас.
5. Создавать `server_received_at` только на сервере. Клиентское время `consent_accepted_at` хранить отдельно и не считать доверенным.
6. Выполнять идемпотентную запись по `submission_id`: повторный сетевой запрос не должен создавать дубль.
7. Сначала успешно записывать обе строки в YDB и только потом отвечать браузеру `ok: true`.
8. Если запись не удалась, возвращать ошибку и показывать пользователю возможность повторить отправку.
9. Не писать имя, телефон или всё тело запроса в логи функции.
10. После записи передавать Cloudflare Worker только название сайта, событие и `submission_id`. Worker отправляет боту сообщение вида `Новая заявка photoprobiz, ID 123…` без персональных данных.

Переменные окружения могут называться, например:

```text
ENDPOINT=grpcs://ydb.serverless.yandexcloud.net:2135
DATABASE=/ru-central1/b1g3rq4isb0l45hg2kg0/etnj5v1s6iavjmndcs7o
DELIVERY_MODE=cloudflare-relay
RELAY_TOKEN=<общий секрет функции и Worker>
```

`RELAY_TOKEN` нужно хранить в переменной функции и в Cloudflare Worker Secret. В режиме `cloudflare-relay` токен Telegram остаётся только в Worker. Секреты нельзя добавлять в Git, Markdown-файл или клиентский JavaScript.

Функция получает краткоживущий IAM-токен прикреплённого сервисного аккаунта из штатного контекста вызова Yandex Cloud Functions и передаёт его YDB SDK. Статический ключ и отдельный пакет metadata service для этого не требуются.

Официальный пример: [подключение к YDB из Cloud Functions на Node.js](https://yandex.cloud/ru/docs/ydb/tutorials/connect-from-cf-nodejs).

## 7. Настройки публичной функции

1. Оставить публичный HTTPS-вызов, иначе браузер клиента не сможет отправить форму.
2. Разрешить CORS только для:
   - `https://photoprobiz.ru`;
   - `https://www.photoprobiz.ru`;
   - локального адреса только на время разработки.
3. Отклонять остальные `Origin`.
4. Сохранить ограничение размера тела, проверку метода `POST`, honeypot и серверную валидацию.
5. Не возвращать в ответе имя, телефон и внутренние сведения базы.
6. Проверить форму через домашний Wi‑Fi и мобильную сеть. Сначала убедиться, что строка появилась в YDB, затем проверить обезличенное уведомление Telegram.

## 8. Работа с заявками

До создания отдельной панели заявки можно смотреть в консоли YDB через запрос:

```sql
SELECT submission_id, server_received_at, name, phone, contact_method, package_name, status
FROM leads
ORDER BY server_received_at DESC
LIMIT 100;
```

После звонка статус можно изменить на `contacted`, после завершения работы — на `closed`. При отзыве согласия нужно найти запись по телефону или идентификатору, удалить персональные данные из `leads` и выполнить предусмотренное политикой действие с доказательством согласия.

Пример удаления рабочей заявки:

```sql
DELETE FROM leads
WHERE submission_id = "идентификатор-заявки";
```

Для регулярной работы удобнее позднее сделать закрытую административную страницу с авторизацией. Публичную таблицу, ссылку без авторизации или выгрузку в Google Sheets использовать нельзя.

## 9. Что указать в документах и Роскомнадзоре

После фактического подключения YDB нужно ещё раз обновить политику и согласие на сайте:

- основная база заявок: Yandex Database, регион `ru-central1`, Российская Федерация;
- обработчик облачной инфраструктуры: ООО «Яндекс.Облако» — точное наименование и реквизиты следует переписать из действующего договора или кабинета;
- Cloudflare используется для DNS, HTTPS, статического трафика и доставки обезличенного уведомления, если этот маршрут сохранён;
- Telegram получает только обезличенное уведомление без имени и телефона;
- GitHub Pages хранит статические файлы сайта и не получает тело формы;
- сроки хранения и порядок отзыва должны совпадать с реальным TTL и ручным удалением.

В уведомлении Роскомнадзора нужно указать реальное место нахождения базы в России и используемого оператора центра обработки данных. Код региона `ru-central1` не заменяет юридические реквизиты: их нужно взять из документов Yandex Cloud. Если уведомление уже было подано со старой инфраструктурой, его следует актуализировать после запуска новой схемы.

## 10. Порядок перехода для photoprobiz.ru

1. Уже выполнено локально: пустая галочка, запрет отправки без неё, отдельные страницы политики и согласия, ссылки у формы и в подвале, версия согласия и идентификатор заявки.
2. Выполнено: создана YDB Serverless `photoprobiz-leads-db` с лимитом 10 RU/с, хранилищем 1 ГБ и защитой от удаления.
3. Выполнено: создан сервисный аккаунт `photoprobiz-leads-sa` и на конкретную базу назначена роль `ydb.editor`.
4. Выполнено: общий `RELAY_TOKEN` сохранён в переменной функции и Cloudflare Worker Secret.
5. Выполнено: версия функции с YDB SDK загружена, подключена к YDB через сервисный аккаунт и проверена рабочим POST-запросом.
6. Выполнено: строгий Worker принимает только обезличенное уведомление после успешной записи в YDB; прежний формат с именем и телефоном отклоняется.
7. Проверить запись, повторную отправку с тем же ID, ошибку базы, TTL и ручное удаление.
8. Обновить политику под итоговую схему и опубликовать сайт.
9. Проверить публичный сайт и форму по Wi‑Fi и мобильным операторам.
10. Подать или актуализировать уведомление Роскомнадзора.

Пункты 2–6 выполнены 11 сентября 2026 года. Контрольный вызов подтвердил маршрут «браузер → Yandex Cloud Function → YDB → обезличенное уведомление через Cloudflare → Telegram». Публикация документов и наличие галочки дополняют эту схему, но не заменяют организационные обязанности оператора персональных данных.
