# Yandex Cloud Function: photoprobiz-leads

## Редакция согласия 12.09.2026

Активная версия функции `d4ee23dmjq2hhq1qhbbr` сохраняет действующую многосайтовую CRM и принимает бизнес-согласия `2026-09-11`, `2026-09-12` и `2026-09-12-2`. Старые варианты оставлены для уже открытых форм; в YDB сохраняется фактически принятая версия без переписывания истории. Новая бизнес-форма отправляет `2026-09-12-2` вместе с укрупнёнными значениями `deviceType` и `osFamily`. Архивы предыдущих документов: `docs/legal/privacy-and-consent-2026-09-11.ts.txt` и `docs/legal/privacy-and-consent-2026-09-12.ts.txt` в корне проекта.

В основную таблицу `leads` добавлены nullable-колонки `device_type` и `os_family`; функция идемпотентно создаёт их при первом обращении к существующей базе. Старые записи отображаются как «Не определено». Полный User-Agent, версия браузера и модель устройства не сохраняются. Подробная сверка, сроки и нерешённые юридические вопросы: `PERSONAL-DATA-REVIEW-2026-09-12.md`. Слово «обезличенное» ниже описывает уведомление без контактных данных и не гарантирует юридического обезличивания связанного ID. Автоматический relay не получает имя, телефон, устройство или ОС; ручное открытие WhatsApp/Telegram по номеру — отдельная передача выбранному сервису.

Функция принимает заявки сайта, проверяет данные и согласие, сначала сохраняет персональные данные в YDB Serverless `ru-central1`, а затем отправляет через Cloudflare Worker обезличенное уведомление в Telegram.

Действующий публичный адрес функции: `https://functions.yandexcloud.net/d4e5ur2fo156lrcve6id`.

Текущая Multi-DB версия опубликована 12 сентября 2026: `d4ee23dmjq2hhq1qhbbr`. Проверка GET
подтвердила `crmDatabasesConfigured: 2`; кабинет прочитал обе базы, а production-проверка удаления
подтвердила отсутствие двух синтетических заявок в `leads`, `lead_meta` и `consent_events`.

Полное руководство: [YANDEX-CLOUD-YDB-PERSONAL-DATA-GUIDE.md](../../YANDEX-CLOUD-YDB-PERSONAL-DATA-GUIDE.md).

## Загрузка новой версии

1. Откройте Cloud Functions → `photoprobiz-leads` → **Редактор**.
2. Выберите Node.js 22 и источник **ZIP-архив**.
3. Загрузите собранный скриптом `build-zip.ps1` архив
   `output/photoprobiz-crm-delete-periods.zip` из корня проекта. В корне архива должны
   непосредственно лежать `index.js`, `storage.js`, `crm-storage.js`, `admin-auth.js`,
   `admin-page.js`, `package.json` и `package-lock.json`.
4. Точка входа: `index.handler`.
5. Таймаут: 15 секунд. Память: 256 МБ.
6. Сервисный аккаунт: `photoprobiz-leads-sa`.
7. Сеть: не выбрана.
8. Добавьте или сохраните переменные окружения:

```text
ENDPOINT=grpcs://ydb.serverless.yandexcloud.net:2135
DATABASE=/ru-central1/b1g3rq4isb0l45hg2kg0/etnj5v1s6iavjmndcs7o
PROINTERIORS_DATABASE=/ru-central1/b1g3rq4isb0l45hg2kg0/etnlahj3qr0l0puq0r1d
DELIVERY_MODE=cloudflare-relay
RELAY_TOKEN=<значение из локального защищённого файла>
ADMIN_BASE_URL=https://functions.yandexcloud.net/d4e5ur2fo156lrcve6id
ADMIN_PASSWORD_SCRYPT=<scrypt-хеш пароля>
ADMIN_SESSION_SECRET=<случайная строка не короче 32 байт>
```

Для нескольких сайтов добавьте необязательную переменную `CRM_SITES_JSON`. Она должна содержать JSON-массив точных серверных правил:

```json
[
  {
    "siteHost": "second-site.ru",
    "label": "Интерьерная съёмка",
    "origins": ["https://second-site.ru", "https://www.second-site.ru"],
    "consentVersions": ["second-site-v1"],
    "formIds": ["homepage", "contacts"],
    "packages": ["", "office", "studio"]
  }
]
```

Не принимайте `siteHost` из тела браузерного запроса. Функция определяет сайт по разрешённому `Origin`, а затем сама записывает доверенное имя хоста. Текущий `photoprobiz.ru` встроен как базовая конфигурация.

`PROINTERIORS_DATABASE` не меняет основную `DATABASE`: заявки бизнес-сайта и ручные клиенты
продолжают храниться в прежней базе. CRM читает обе базы, а статус и заметку записывает только
в ту базу, которой принадлежит заявка. При совпадении UUID в двух базах изменение отклоняется.
Сервисному аккаунту `photoprobiz-leads-sa` требуется `ydb.editor` на обе базы; доступ к
`prointeriors-leads-db` назначен на уровне этого ресурса.

`RELAY_TOKEN` должен совпадать с одноимённым Cloudflare Worker Secret. Не помещайте его в код, ZIP, Git, Markdown или скриншоты. Telegram-секреты функции в режиме `cloudflare-relay` не использует.

Авторизация в YDB использует краткоживущий IAM-токен из контекста Cloud Function. Яндекс автоматически добавляет его, когда к версии прикреплён `photoprobiz-leads-sa`; статический ключ и отдельная SDK для metadata service не нужны. Переменная `YDB_METADATA_CREDENTIALS`, если она осталась в старой версии, не используется и может быть удалена позднее.

9. Сохраните изменения и дождитесь состояния новой версии **Active**.
10. Публичный вызов функции должен остаться включённым.

## CRM-кабинет заявок

Адрес: `https://functions.yandexcloud.net/d4e5ur2fo156lrcve6id?admin=1`.

Пароль и значения трёх переменных администратора хранятся только в локальном защищённом файле `%LOCALAPPDATA%\photoprobiz\admin-cabinet-credentials.txt`. В GitHub, ZIP и документацию их не добавляют.

Кабинет отдаётся самой Yandex Cloud Function и не загружает сторонние шрифты, скрипты или аналитику. До входа персональные данные не передаются браузеру. После входа подписанный токен сессии сохраняется только в `localStorage` этого origin и передаётся закрытому API в заголовке `X-Admin-Session`; секрет подписи и пароль остаются на сервере. Такой вариант нужен потому, что прямой HTTPS-вызов Yandex Cloud Functions фильтрует заголовки `Cookie`/`Set-Cookie`.

CRM поддерживает:

- просмотр всех подключённых сайтов или одного сайта;
- выбор месяца с группировкой по годам, поиск по имени/телефону, пагинацию и статусы `Новая`, `Связался`, `Завершена`;
- ручное добавление клиента из рекомендации, соцсети или другого источника;
- собственную заметку и источник в карточке;
- две основные кнопки на телефонах/планшетах и три действия на компьютере;
- единое меню WhatsApp, Telegram и MAX;
- индивидуальное и массовое безвозвратное удаление заявки и связанных строк.

Кнопка Telegram использует телефонную ссылку; результат зависит от настроек приватности аккаунта клиента. У MAX нет документированной прямой ссылки на профиль по номеру, поэтому CRM сначала копирует номер, а затем открывает официальный `https://max.ru/`. Если приложение поддерживает перехват универсальной ссылки, переход продолжится в нём; иначе откроется сайт.

Авторизация скользящая: каждый успешный запрос кабинета выдаёт новый подписанный токен на 90 дней. Пароль потребуется снова только после 90 дней бездействия, ручного выхода, очистки данных браузера или смены `ADMIN_SESSION_SECRET`.

Cloudflare Worker получает только ID и служебное время. Кнопка `Открыть заявку` в Telegram ведёт в кабинет Yandex; имя и телефон по-прежнему не проходят через Cloudflare и Telegram.

При первом запросе функция автоматически создаст таблицы `leads`, `consent_events` и `lead_meta`
в основной базе. В интерьерной базе таблицы заявки и согласия создаёт функция интерьерного сайта,
а CRM при первом чтении создаёт только собственную `lead_meta`. У `leads` и `lead_meta` настроено
удаление по `expires_at` через один год, у `consent_events` — через три года. Веб-заявка атомарно
записывает строки заявки и согласия, а затем вызывает Worker. Ручной клиент записывается в основную
базу с `site_host=manual.crm`; фиктивная строка согласия сайта для него не создаётся.

Для существующей основной `leads` функция перед чтением или записью проверяет наличие `device_type`
и `os_family` и добавляет отсутствующие поля как nullable через `ALTER TABLE`. Пересоздание таблицы и
перенос старых заявок не требуются. Для ручных клиентов записывается `unknown`; значения новой
бизнес-формы принимаются только из серверных allowlist.

Закрытые операции CRM:

| Операция | Назначение |
| --- | --- |
| `GET ?admin_api=sites` | Сайты для фильтра |
| `GET ?admin_api=periods&site=<host>` | Доступные месяцы всех или выбранного сайта |
| `GET ?admin_api=leads&site=<host>&period=YYYY-MM` | Список с фильтром сайта и месяца |
| `GET ?admin_api=lead&id=<uuid>` | Карточка |
| `POST ?admin_api=manual` | Ручной клиент |
| `POST ?admin_api=notes` | Заметка и ручной источник |
| `POST ?admin_api=status` | Статус |
| `POST ?admin_api=delete` | До 50 уникальных ID для окончательного удаления |

Все операции требуют корректный `X-Admin-Session`; POST дополнительно проверяет `Origin` кабинета.

Удаление сначала определяет базу-владельца каждого ID. Совпадение одного ID в двух базах отклоняет всю операцию с HTTP 409. Внутри одной YDB строки `lead_meta`, `consent_events` и `leads` удаляются одним многооператорным DML-запросом и одной транзакцией. Между двумя YDB общей транзакции нет: API возвращает `deletedIds` и `failedIds`, а интерфейс оставляет не удалённые карточки выбранными. Уже отсутствующий ID считается успешно удалённым состоянием. Интерфейс автоматически делит выборку больше 50 записей на запросы по 50.

GET по адресу функции должен вернуть:

```json
{
  "ok": true,
  "storage": "ydb",
  "databaseConfigured": true,
  "crmDatabasesConfigured": 2,
  "deliveryMode": "cloudflare-relay"
}
```

## Проверка после развёртывания

1. Откройте адрес функции по Wi-Fi и через мобильную сеть.
2. Отправьте одну тестовую заявку с сайта.
3. Убедитесь, что сайт показал успешную отправку, а Telegram прислал только ID заявки без имени и телефона.
4. Откройте YDB → `photoprobiz-leads-db` → **Навигация**: должны появиться таблицы `leads`, `consent_events` и `lead_meta`.
5. В CRM проверьте фильтры сайтов и месяцев, поиск, карточку, меню мессенджеров и технические данные.
6. Создайте только синтетические записи. Проверьте индивидуальное и массовое удаление и убедитесь, что они исчезли из CRM и трёх связанных таблиц YDB. Не удаляйте реальные заявки.
7. Выполните запрос:

```sql
SELECT submission_id, server_received_at, name, phone, contact_method, package_name, status
FROM leads
ORDER BY server_received_at DESC
LIMIT 20;
```
